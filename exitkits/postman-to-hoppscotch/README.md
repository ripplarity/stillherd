# postman-to-hoppscotch: import a Postman collection into a self-hosted Hoppscotch, with a signed record of network egress

`bash kit.sh` boots the Hoppscotch recipe (`selfhost/selfhost.sh postman`), imports `sample/collection.postman.json` (Postman v2.1, 5 requests, one bearer-auth collection setting) and `sample/environment.postman.json` (2 variables), checks that the 5 requests are listed by the backend, and tears everything down with volumes removed. The whole sequence runs inside one `silent/silent.sh` window, which writes `results/attestation.json`, an ed25519-signed list of every external host the proxy saw and the request bytes forwarded to them.

## How the import is done

Hoppscotch's Postman importer exists in the browser application only (it is part of the minified web bundle; the backend image contains no importer). This kit does not drive a browser. `convert.py` maps the Postman fields listed in its header (name, method, URL, headers, raw body, bearer auth, `{{var}}` to `<<var>>`) to Hoppscotch's collection format, and `kit_import.py` sends the result to the backend's own `importUserCollectionsFromJSON` and `createUserEnvironment` GraphQL mutations after signing in through the backend's REST sign-in endpoints. So the mapping is this kit's, not Hoppscotch's importer. Fields not mapped (scripts, query parameters as separate rows, form-data bodies, folders' own auth) are not carried over.

Setup steps the kit performs on the fresh instance: it completes the first-run onboarding through `POST /v1/onboarding/config` (email sign-in enabled, mail server set to a local sink, `smtp_sink.py`, that discards mail); it restarts the application container so the setting is read; it requests a sign-in link for `kit@example.test`, reads the one-time token from the instance's own database with `docker exec`, and verifies it to get a session.

## Limits

- Proxy-visible traffic only. Traffic that ignores the proxy environment variables, non-HTTP protocols and DNS lookups are not recorded. The mail from the application to the local sink uses SMTP to the host and is not seen by the proxy; it stays on the local machine by construction.
- The image digests above are those of the pulled images at run time; pulling happens before the recorded window, outside the proxy, so the registry hosts used to download images are not in the attestation.
- `attestation.json` records the command `bash selfhost/recipes/hoppscotch/smoke.sh`; the import steps are inside that script, generated by `selfhost/selfhost.sh` from `kit_import.py`. The attestation shows the window's hosts and bytes, not which steps ran inside it.
- One run, one sample collection of 5 requests; no timing or scale claim. A real collection can use fields this converter drops.
- The application image is the `latest` tag at run time; the digest above identifies it.
- Hoppscotch was not asked to confirm any behaviour described here.
